## Plan

The preceding goal turn made progress: E-64's ordered cache/refresh handling, 29 added regressions, 1,092 passing tests and exact signed/refined APK with installed Retry and silent preparation evidence. Customer readiness remains unproven. This pass addresses its explicitly open native store lifecycle findings on both platform sources; no purchase, paid-provider call or receipt/key inspection is authorized by the test plan.

1. Preserve the existing library, cache schema, SDK versions and signed APKs. Inspect the actual native module/Expo dispatch contracts. Reproduce native request ownership, teardown, timeout, exception and stale-checkout paths against production coordination code with synthetic ports.
2. Reserve native interactive ownership before lookup. Bound read/preparation work, settle every admitted request once, suppress stale callbacks and close SDK connections deliberately. Keep system checkout waiting distinct from a timed-out lookup; a timeout must not launch a second checkout or imply cancellation of provider charges.
3. Marshal Android requests and callbacks to the main queue. Validate offers safely and use a fresh visible Activity for checkout. Add a one-way dependency from optional commerce to the existing audio admission coordinator, never an import from playback to commerce. Add separate idle generations/preparation leases without changing transport command epochs or DSP scheduling. A prepare/disarm round trip invalidates old checkout preparation even after the app is idle again.
4. Apply matching iOS ownership, cancellation and admission checks before StoreKit calls, with no lock held across an async StoreKit operation. Preserve completed transaction recovery through the platform's current-entitlements flow; destroyed module owners cannot publish into a new interface. System purchase UI timing, signed transactions and refunds still need configured store accounts and physical/Xcode evidence.
5. Run native coordination and existing audio admission regressions, software/architecture/translation checks and Android native build/lint. Inspect packaged source/native changes, use only the owned synthetic emulator, complete the single `crit` loop and record exact results and limits. A native fixture is not an App Store/Play transaction.

## Contracts retained

The intervening E-65 closure-protection turn was progress: 35 added cases, 1,127 passing shared tests, Android release/lint and exact installed/refined APK with locked notification, power-policy and silent relaunch evidence. Its native/core changes remain the candidate baseline. The incomplete commerce work was deliberately excluded from that APK and is resumed here.

The actual-module harness reproduced five additional Android failures: an already-owned purchase reopens checkout; pending ownership reopens checkout; unspecified ownership is reported as not-owned; an unknown record can conceal a pending one; and raw purchase accepts a blank localized price. Fixes first passed 34 cases; the final actual-module corpus passes 41. Native verified/reported ownership carries a bounded ephemeral delivery handle, shared SQLite commits ownership first, and only then does an idle native confirmation acknowledge/finish the transaction. Failed saves or stale/live results do not finish it; Restore can recover from the store. Receipt material never crosses this bridge or enters backups.

Apple's [finish contract](https://developer.apple.com/documentation/storekit/transaction/finish%28%29) requires delivery before finishing. Early native finishing has been removed from both purchase and current-entitlement reads. The matching iOS source uses the same explicit delivery-confirmation contract; its compiler/device gates remain open. No actual transaction has been performed.

Free preparation/playback never awaits a store connection or entitlement. GO/panic, local media, immutable snapshots, controller ownership, explicit recovery, schema v2 and existing music tuning remain unchanged. Optional store lookup failures are retryable. Once a user has handed an action to the system checkout, closing an interface cannot promise cancellation of that system action; later paid results must remain recoverable through the store. New SDK calls that present checkout require fresh native admission. No audio lock may be held across an async store/network wait.

Primary contracts: [Google Billing integration](https://developer.android.com/google/play/billing/integrate) requires main-thread checkout; [Apple current entitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements) excludes refunded/revoked purchases and retains non-consumables; [StoreKit In-App Purchase](https://developer.apple.com/documentation/storekit/in-app-purchase) separates verified transactions, pending results and transaction updates. The actual resolved Billing dependency remains 9.1.0. iOS compilation and system-store behavior remain explicit gates on this Windows host.

## Implementation and acceptance

Android requests and SDK callbacks run on the main queue. Each native owner has a bounded request table, one-shot settlement, connection generation, lookup deadlines and immediate teardown exclusion. Purchase/Restore reserve interactive ownership before lookup. Checkout requires a freshly visible, focused Activity after asynchronous reads. An already-owned or pending item cannot open another checkout; unsupported matching ownership stays unknown. A system checkout already awaiting the user deliberately does not use the lookup timeout, which could otherwise admit a duplicate checkout.

Both platform coordinators now distinguish idle admission generations and pending preparation leases from the transport command epoch. Preparation, diagnostics and arm/disarm transitions invalidate stale store preparation. Releasing a lease does not invalidate audio commands. Android's final SDK handoff is a short synchronous admission section; no audio lock spans a store/network await. The actual runtime releases preparation leases after refusal, cancellation, start failure and attachment completion. The iOS source has corresponding owner/task cancellation, scene validation and preparation admission, but has not been compiled here.

Delivery confirmation uses opaque, bounded, process-local handles. Android acknowledges and iOS finishes only after the local ownership save succeeds and a fresh idle admission succeeds. Timeouts retain retryable delivery; late callbacks cannot remove a newer confirmation request. Finished-token/transaction observations prevent stale unconfirmed snapshots from reopening a completed delivery within that owner. A later authorized purchase result may be saved during a critical session, but it cannot start a new confirmation SDK call or live store event. Pending purchases never grant ownership or get acknowledged.

The shared interface contains synchronous native-load failures, refreshes only while focused and idle, rejects superseded metadata callbacks, and removes foreground/native observers on blur. It retains ordered durable saves, joins bounded refresh observers, reports a saved-but-unconfirmed result distinctly, and never caches a delivery handle. The new status is translated in all ten languages. No persisted song/cache schema, external SDK version, GO/panic position, media processing or provider configuration changes.
