# Show-protection language · 24 October 2026

## Plan

The owner requested practical safeguards against premature closure. The existing Android prepared-show foreground service, quiet ongoing notice, battery/standby/permission/channel/heat observations and deliberate repair actions remain the foundation. Installed testing found that choosing Arabic in the app on an English Android system leaves the native battery warning in English.

1. Capture the app's chosen presentation language in the runtime-only preparation envelope. Keep library/song schemas and immutable cue settings unchanged. Older callers without that value retain Android's system-language fallback.
2. Resolve the notification's safety text, channel label and transport actions using a service-local resource context for the admitted show. Do not change Android's device/app locale, recreate its Activity, start an idle service or request permission automatically. No language change may dispatch transport.
3. Reject unsupported presentation values by falling back to system resources. Cover preparation capture, legacy callers, ten languages, invalid values and native policy. Verify the exact installed APK's Arabic/Hebrew warnings, explicit permission flow, locked Ready retention, quiet flags, deliberate exit and unchanged GO/panic positions.
4. Preserve all language resources offline in Android App Bundles through the source-owned Expo plugin. A host-build assertion must verify the effective language-split setting, alongside plugin regeneration/invalid-configuration tests. This addresses the native build's real `AppBundleLocaleChanges` finding; the standalone library's narrow suppression is conditional on that checked host contract, not a global lint exclusion.
5. Installed Hebrew verification exposed a separate packaging defect: Expo's `b+he` filter dropped libraries' legacy `values-iw` resources. Keep that legacy qualifier alongside the supported app language, verify it in the host DSL and inspect every finished APK's nine nondefault language configurations. Source dictionaries alone do not prove translated resources reached the binary.

## Delivered behavior

Explicit preparation captures the current app language into the runtime-only native envelope. Android uses a service-local resource context for warning text, channel naming, media metadata and transport labels. Older/unsupported presentation values use system resources. Changing the next presentation language does not rewrite an already prepared owner, dispatch commands, change the phone's locale or recreate its Activity. Reconciliation strips presentation metadata from the canonical immutable snapshot and never replays preparation or audio.

The existing native safeguards remain: a quiet ongoing foreground notice throughout a deliberately prepared show, including Ready/Paused; independent battery/standby/notification/channel observations; combined heat/low-charge/restriction warnings; unknown-reading guidance; direct idle-only repairs; fresh observations on Settings return; and deliberate silent recovery after termination. Nothing starts an idle service, changes permissions/settings automatically or promises immunity from user/system termination.

The Expo plugin retains all native presentation languages offline and explicitly preserves legacy Hebrew resources alongside the `b+he` filter. It is idempotent, upgrades only its exact earlier block and rejects unsupported/incomplete generated configuration. Host builds assert both disabled language splitting and the legacy Hebrew filter. The standalone library's locale-change suppression is narrowly documented against that checked host contract. Finished-APK language inspection complements dictionary parity; source translations alone missed the original Hebrew packaging defect.
