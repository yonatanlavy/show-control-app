# Download completion metadata instrument

Separate same-public-test-signer instrumentation for `app.showcontrol.working` on the root-owned `emulator-5564` / `ShowControl_SingleButton_QA`. It is not bundled in Show Control. It does not launch MainActivity/React, initialize yt-dlp, request audio focus, call providers or access the network. Android starts only the target Application; omitting React prevents foreground download recovery from importing the metadata fixtures into the library. Its one service case starts only the existing non-exported ShowDownloadService with explicit `cancel` action and a fresh unknown job ID; it never starts a transfer.

Begin with no other instrumentation or target service, and no active or ready original download. The instrument requires a fresh, unused DownloadRuntime, empty process/cancellation maps, no search, no AtomicFile backup/pending write, and a bounded terminal-only original history. It holds the runtime's own synchronization monitor throughout the policy scenarios. Do not interact with the app or introduce another producer while it runs; any observed foreign work fails closed. Original job metadata is hashed logically, including history order and sorted object keys. It never opens original media, the library database, secure storage or API keys. A previously absent jobs.json may become an empty native-managed metadata file; byte-for-byte file identity is not claimed.

Thirteen metadata cases exercise actual production cancel/complete methods: ready completion; repeated completion; cancellation after attachment; ready cancellation provenance; repeated cancellation; completion of a simulated SQL-committed claim after cancelled-ready staging is gone; incomplete/legacy cancellation refusal; strict string/numeric marker refusal; wrong URI and malformed byte-count refusal; and the actual start-input completion-field sanitizer. The sanitizer is called directly without start(). A fourteenth case verifies that an accepted idle stale-cancel service start stops itself. Tiny UUID-owned `audio.mp3` files are metadata fixtures, not decoded/valid MP3 acceptance evidence. There is no SQL commit in this instrument: the test supplies that claim to complete(), as its caller normally does. This is native metadata/service-policy evidence, not an end-to-end download/import, SQL race, JavaScript, physical-device or iOS proof.

Fixtures use fresh random job IDs, exact canonical child directories, ownership markers and hashed original test bytes. Only those record objects are injected, checked and removed. Cleanup calls production remove() only for the same owned terminal record after checking every remaining file. Runtime cancellation entries left by remove() are cleared only for the exact AtomicBoolean reference created by the probe's own cancel(), with no process present. The idle service case requires no service before admission, an accepted exact component, and an empty unchanged runtime/history. ActivityManager observes only the target UID's services. If the old service remains, the failed assertion is retained; cleanup may stop only that one helper-started, non-foreground, started service after component/PID/UID/birth-time and unchanged-runtime checks. Any new owner/work is preserved. Unexpected records, directories, bytes or reference changes are preserved and reported. No helper performs recursive filesystem deletion.

Build with `build.ps1 -Sdk <sdk> -Jdk <jdk> -DebugKeystore <public-test-key> -TargetApk <exact-release-apk> -Output <fresh-path>`. The target/helper test certificate must match. Install only the helper after verifying the target. Invoke `invoke.ps1 -RunId <fresh-lowercase-uuid> -ExpectedApk <same-apk> -ProbeMetadata <output/metadata.json> -Scenario all`. `-Scenario idle-cancel` runs only the one idle-service case and does not link/call new completion/sanitizer methods, allowing a bounded baseline check on the older APK. A baseline leak is expected to fail; cleanup success does not turn the assertion into a pass. Rebuild helper metadata against the final APK before its full validation. Scripts verify exact serial/AVD, package, source/manifest hashes and installed target/helper APK SHA-256. Existing probe guards are untouched.

Retain `.native-check/download-completion-run-<uuid>/{handle.json,instrument.out.txt,instrument.err.txt,terminal.json}`. Passing requires the selected 14 or 1 cases, `passed=true`, `originalJobsUnchanged=true`, `ownedFilesRemoved=true`, `ownedRecordsRemoved=true`, `nativeRuntimeIdle=true`, `idleServiceRemoved=true`, equal logical before/after digests, `INSTRUMENTATION_CODE: -1` and a recognized empty post-run service dump. Service observations and a leaked-service assertion are retained even after safe cleanup. Runtime work is bounded to 40 seconds; a host observation deadline retains the live process handle instead of restarting it. Missing/partial evidence is not a pass. After inspection and confirmed idle, uninstall only `app.showcontrol.downloadcompletionprobe` and verify normal silent relaunch. The separate test helper never changes the production APK.
